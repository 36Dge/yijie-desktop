# 已访问会话反复整页加载修复

## 结论与原因

用户截图中的“正在读取本地对话”是会话正文的加载状态。此前的媒体缓存仅复用图片与
视频元素，无法复用整份对话阅读状态。

`selectSessionInternal` 每次切换都执行 `clearSelection()`，将 `history`、
`conversationState`、原生显示投影和审批观察状态清空，再依次读取会话用途、控制面、
草稿、订阅、resync、适用的产物历史及原生视图。ChatPage 在没有历史和时间线时显示
整页加载提示。没有最近访问会话的阅读缓存，因此 A→B→A 与首次进入 A 使用同一条
空白展示路径。这是本次确认的直接原因，不是磁盘丢失对话，也不是旧启动入口。

原生握手、订阅、历史协调与权限检查仍承担状态同步职责。本次没有为了取消加载页而
跳过这些步骤，也没有给 Runtime 或 Host 增加第二套执行或恢复机制。

## 实现范围

`contract-impact = none`：只改变 Desktop Renderer 的内存阅读投影及其调度，原有
Native IPC、Host/Runtime 协议、鉴权、发送/审批资格、历史与事件持久化格式不变。
纯页面及 store 改动，不需要契约生成、原生构建或跨仓迁移。

- 离开已成功加载的会话时保存阅读快照，最多 8 个、估算 32 MiB，按最近访问顺序淘汰；
  超过单次预算的快照不缓存。只在当前进程内保存，不写 localStorage、磁盘或数据库。
- 返回时立即提供 `readingView` 给页面，同时沿原链路核对最新历史。权威 `history`、
  control plane、subscription 和 selected access mode 仍从空状态重新确认；
  `canSend`、`canDecideApprovals` 和原生活跃轮次不从缓存恢复。
- 缓存按 context/session 核对，登出、上下文变化、读取权限撤回、已观察到的拒绝、
  删除/cleanup 与当前刷新失败会清理相关快照。异步结果继续使用既有 selection epoch，
  A 的迟到响应不能覆盖 B。
- 文本、历史附件身份及产物引用一同恢复，已有媒体缓存与原生资源有效期继续生效。
  发起草案、审批和发送仍使用真实当前状态；缓存不能赋予这些操作资格。
- 页面把阅读历史、正文、审批展示等拆成稳定的 computed 字段，避免聚合对象变化突破
  原流式按帧合并机制。原来每帧一次的时间线渲染及滚动跟随保持。
- 旧版推理详情读取使用独立的、按选择核对的读取控制器，成功读取不再中断后台会话
  刷新。错误仍按原页面错误阶段处理，旧选择的结果丢弃。

首次打开、缓存已淘汰、应用重新加载或权限上下文重建后，仍可能出现首次加载。
后台核对保留，因此不能把这个改动描述为“切换时完全没有读取”或“持久缓存所有聊天”。
