## 根因与证据

1. `src/api/chat-conversation-adapter.ts:36,178` 为产物创建独立 `kind: artifact` 产品记录，并使用 `1000 + artifact.ordinal` 排序，避开原生 Item 的序号范围。它们已经有明确的 session/turn/artifact 绑定；独立存储不意味着必须独立于回答展示。
2. `src/stores/chat.store.ts:1979` 和 `src/domain/conversation-view.ts:444,483` 将产物引用保留并合入同轮只读视图，原生 Item 与产品记录不互相伪装。读取历史和当前产物刷新都经过此路径。
3. 原 `conversationActivityPresentation → ChatTurnGroup → ChatActivityRow` 将每个 artifact 当作顶层阅读条目。正文自己的 `ChatTimelineItemShell` 已先渲染底部操作栏，后面的产物继续单独渲染。因此即使所有文件早已存在，阅读顺序仍固定为“正文 → 复制/评价/模型 → 文件”。
4. 修复前在当前正常运行的开发 App 原历史中实际复现：九文件与四文件都位于各自回答操作栏之后，且是回答容器的同级条目。修复后同一客户端热更新、离开后重新打开同一历史，均为“正文 → 本轮全部文件 → 回答操作”。

直接根因是阅读层缺少回答与产物的组合，而非文件缺少轮次归属。本审计不以页面位置推断原任务中每个文件实际生成、接收的时间；没有声称重新审计供应商的全部时序日志。

## 实现

- `conversation-turn-output.ts` 只对同 session、同 turn 的产物做阅读组合，关联本轮最后一个可读回答；保留原 Item、block、身份及产物顺序，不根据文件名或正文猜测归属。只有工具前言时不把它当最终回答；没有正文时仍立即展示已有产物。
- `ChatTurnOutput.vue` 将原正文组件、原产物组件置于同一个回答内容区域，统一把该回答的原操作槽放到内容之后。没有新增下载、预览、内容解析或执行机制。
- 输出分组和产物各有稳定 key。文件先到、文字后到时，已有产物组件及容器保持同一实例；文件晚到、历史重建时仍只展示一份。
- `tailCommentaryCandidate` 忽略产品产物的独立尾部序号，避免最后一条已有公开文字仅因产物随后出现而被折叠。它不改原 phase，也不为 commentary 新增最终回答操作。
- 原操作栏显隐规则提取为 `showConversationItemActions` 供普通回答和组合回答共用，保留流式未完成、工具前言、结构化结果的原限制。
- 原生复用依据：固定候选来自 `contracts/runtime-tool-search.candidate.json` 的 Codex 0.144.6；`yijie-codex/codex-rs/app-server-protocol/src/protocol/v2/item.rs` 的 `AgentMessage` 保留原 text/phase。现有产物发布、Native 接收、原生文档预览与另存全部沿用，无 Runtime 修改。
