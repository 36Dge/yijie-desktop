用户本轮要求：创建后默认开启，不再单独授权；开关直接启停并 toast；简化卡片。
这取代 FEAT-155 旧交互中「保存暂停→填写次数/截止时间→确认授权」的用户步骤。
现有 Ask、租户、原生权限重验、工具审批、unknown 阻断及生命周期边界继续生效。

contract-impact = semantic。Owner：段成威（本轮明确需求）。producer/consumer：同包
Desktop Rust 与 Vue；公共 API / Host / Contracts wire = N/A，未改其 schema 或协议。
本地权威为 `src-tauri/schemas/scheduled-task-ipc-v1.schema.json`；派生物通过
`node scripts/generate-scheduled-ipc.mjs` 生成，候选摘要在
`contracts/scheduled-ipc.candidate.json`。只做本地候选，未提交、发布或迁移用户库。

新增 `schedule_save_active_plan_v1`、`schedule_confirm_active_draft_v1`、
`schedule_enable_plan_v1`；请求/响应复用现有同源类型，均要求当前 schedule.run，
写入再次验证 manage/run。需要现有 SQL24+；不升级 schema，不改历史 migration。
旧保存/确认/有限授权命令保持原语义。新 UI 和 native 随同一 Desktop 包更新。

创建及启用使用同一数据库事务；失败回滚计划、grant 和回执。创建即记录计划执行意图，
重复计划复用现有 grant 格式的整数/日期上界（2147483647 次，9999-12-31），
一次性任务为 1 次；用户不再填写额度和期限。实际运行仍需原生 authority、可用目标、
Ask 和执行服务。保存不调用模型、不创建执行聊天、不触发立即运行。
新计划开启；编辑已有计划保留其开启/关闭状态。已有暂停计划不自动迁移为开启。
同请求重试只返回当前状态，不重复 grant、不重新开启后来关闭或删除的计划。
草案重复确认也只读回原计划。后台未就绪时先保存开启意图，页面准备执行服务；
准备失败显示明确恢复入口，不谎报已运行。应用关闭或电脑休眠期间不保证执行。

回滚到支持 SQL24+ 的兼容 reader 保留记录与 grant；若需要停止新语义计划，先用正常
关闭开关暂停。不能降级数据库或把旧版再次授权回执当成新的创建意图。

UI 使用既有 Naive Switch 和 token：石墨滑块（暗色关闭时为浅色）、浅灰关闭轨道、品牌青柠开启轨道，
无静态描边和阴影，保留键盘焦点。卡片保留标题、最多两行内容、时间规则、下次执行
或关闭原因；运行目标在编辑弹窗中查看。历史/立即运行/删除仍可键盘访问。

验证结果见本任务最终记录。只运行正常、非破坏性测试；全量 Rust 测试中包含

## 卡片立即执行调整（2026-09-25）

按用户要求，卡片「立即执行」点击后直接准备本地执行服务、读取最新计划，并沿现有
单次许可/原生执行接口提交一次运行，不打开「确认运行一次」弹窗。原生请求受理后
显示可关闭的 success toast「任务已开始执行」。普通成功不插入大段授权说明或临时

查证/重试入口，不自动再次提交。提交中按钮 loading 并阻止重复点击。

明确授权）。现有 IPC、公共 Host/API、持久格式、单次许可、Ask 和工具审批均未改变；
不新增 native command 或依赖。执行记录里的「重新执行」保留已有差异审阅流程。
新增正常流程测试覆盖直接启动、回执前不提示成功、重复点击保护、服务准备失败、
提交拒绝与结果不确定时的只读查证；不执行破坏或攻击注入测试。

## 历史清理阻塞与执行提示修复（2026-09-26）

contract-impact = semantic：修复本地持久化删除作业的读取/恢复行为，未改 IPC、
Host/API 请求响应、错误码、权限、单次许可或数据库格式。权威源为本仓
`src-tauri/src/chat/database.rs` 的删除作业与 outbox 实现，兼容既有基础 schema 15
及定时任务 schema 26、outbox payload v1/v2、删除回执 v1。公共 contracts PR、
consumer pin 均为 N/A（没有公共 wire 变化）；唯一 producer/consumer 是 Desktop
原生存储与清理协调器。无跨仓修改、迁移、新依赖或新 command。

只读诊断确认：活跃轮次、有效待发送操作、有效任务绑定、定时执行占位均为零；
一条已取消聊天的删除作业持续 pending。该聊天只重试过创建空闲会话，未生成或
投递 start_turn，也没有 Runtime 执行绑定。删除时 submission_status 已变为
cancelled，但 status 保留 queued，旧 claim_next_deletion 永远拒绝认领该作业，
而全局占用检查又把未完成删除视为忙碌，因此形成持续阻塞。

修复仅允许有确切 outbox 证据的「已取消、未开始执行、无原生轮次绑定」通过旧
queued 状态检查，继续走既有认领、Host/Runtime 清理、本地清理、删除回执流程。
创建空闲会话的重试不等于已投递执行指令；start_turn 曾被认领/投递、结果不明、
已绑定或 streaming/stopping 的记录继续阻塞。未知 payload 版本保守阻塞。
定时任务已确认释放的历史轮次仍遵循原 scheduled_quiescent 规则。未直接修改用户
数据库，未伪造执行完成、清理回执或释放占位。

升级：无需迁移，已有 pending 作业由正常协调器恢复。回滚：schema、payload 和
回执不变，旧 reader 可读已完成的清理回执；尚未处理的旧 queued/cancelled 作业
回滚后可能再次遇到原阻塞。历史执行状态不被改写，远端清理确认仍是本地删除的
前置条件；原先无 Host 映射的处理方式保持不变。

运行、待确认状态或后台清理，不再断言一定有聊天正在执行。成功刷新、切换上下文
或删除任务后的列表更新会清除已明确失败的旧反馈；刷新失败则保留原错误。
