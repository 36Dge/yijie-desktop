# 无项目任务

## 本地边界设计

用户未选择本地项目时，可发送有效文本或就绪附件。普通任务权限、运行环境就绪、提交互斥和附件限制保持有效。创建请求显式传入 `projectId: null`；应用在自己的 Chat 数据目录下创建按租户、用户和提交操作隔离的受管工作目录，不使用进程当前目录或其他用户项目。

`contract-impact = breaking`（仅 Desktop 本地 IPC / 私有数据库版本边界）：现有 UUID 项目请求和会话保持原义，新增 null 请求及会话投影；旧前端不能解释新 null 值，前端和原生端必须随同一应用构建一起交付。API / Agent Host / Runtime wire、权限 capability 均不变；contracts PR / consumer pin 为 N/A，因为权威源位于本仓 `src-tauri/schemas/chat-ipc-v1.schema.json`、`chat-ipc-v2.schema.json` 及 migration 0027。

Native 保留内部项目 UUID 供 Runtime 工作目录、幂等与历史关联使用，以 `workspace_source=managed_chat` 区分受管目录。IPC 对无项目会话仅投影 `projectId: null`，不暴露路径，也不把可用状态伪装为“已移除”。项目选择器不列出内部工作目录。顶层任务与目录任务复用相同会话功能。

首次无项目提交按正常 migration 流程升级至 schema 27；既有记录不改写。当前新版 reader 可重新打开 27，既有日程 reader 也识别 27。旧应用最高 reader 为 26，不能直接打开升级后的数据；不执行数据库降级或手改 migration ledger。回滚须使用支持 27 的兼容应用构建。初次实现的开发验证使用临时合成数据；实际使用无项目任务时由应用正常迁移至 27，不手动修改用户数据库。

无项目会话在任务记录顶层显示，排在目录之后、已移除目录历史之前；内部沿用原始任务列表顺序。既有“任务目录”分组和已移除目录历史规则保留。

## 2026-09-26：从历史任务返回新建任务的目录状态修复

本次修复 `contract-impact = none`：仅纠正 Desktop 新建任务的选中状态与实际提交参数，既有 null/UUID IPC、API/Host 协议及本地持久状态格式均不变。

真实窗口复现路径：打开一个目录已移除的历史任务 → 返回“新建任务” → 输入“今天周几？”并发送。历史任务 watcher 将旧 projectId 写入新建任务的选中状态；返回新建任务时没有清空。Composer 按可用项目列表展示“选择本地项目”，提交却仍使用隐藏的旧 ID，在原生项目复核阶段返回 `chat_resource_not_found`，因而显示“任务不可用”。请求在进入无项目创建前就已失败。

修复后的新任务只使用自己的目录选择状态：默认不选目录，不继承历史任务目录，不自动挑选第一个历史项目。退出会话返回新任务或切换授权上下文时清空；显式选择的可用目录正常使用，目录移除或失效后清空，不能替换成其他目录。界面与提交共同使用同一份可用项目投影，界面显示未选择时，创建请求必须传 `projectId: null`。

新增回归在修复前明确失败（预期 null，实际为历史目录 ID），修复后通过。同时覆盖新任务在已有项目列表时仍不默认选择、无目录发送、显式选目录发送、目录失效不自动切换、提交失败保留输入。


本次验收：6 项页面定向回归通过，2 项 store 的 null 项目创建回归通过；`pnpm lint`、文档构建及 canonical 应用构建通过。实际原生窗口中先复现失败，再重新构建启动：从目录已移除的旧任务返回新建任务，确认显示“选择本地项目”，通过发送按钮成功创建顶层任务并收到回复；无目录会话继续发送也收到回复。只读元数据核对确认使用 `managed_chat` 工作区、数据库按应用流程升级为 27、Host/Runtime 绑定成功，已有目录任务仍保留。验证输入仅要求简短回复且不调用工具。
